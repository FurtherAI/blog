Prefix Tree Packing in ART

August 2026 · ART / Megatron

A training batch has a lot of structure: many completions per prompt in a GRPO or CISPO group, a system prompt repeated across otherwise-unrelated tasks, several SFT completions distilled from one source. Whenever two sequences in the batch share a token prefix, encoding that prefix twice is wasted compute for any token mixing layers that are causal. ART packs the batch as a radix tree instead of a list of sequences, then solves a bin-packing problem to fit that tree into fixed-length training rows (the fixed length has a maximum set by the available VRAM, which is usually what you're configuring it to for highest MFU, but you may choose to keep it smaller for sample efficiency).

The tree

Treat each tokenized sequence as a root-to-leaf path. Two sequences that agree on their first k tokens can share one node covering those k tokens; where they disagree, the tree branches. Building this shape is a small recursive procedure: find the longest run every active sequence agrees on, emit it once, then partition the rest by their next token and recurse on each partition. 

def build_segments(sequences, start=0, parent=None):
    active = [s for s in sequences if len(s) > start]
    if not active:
        return
    end = start
    while end < min(len(s) for s in active) and len({s[end] for s in active}) == 1:
        end += 1
    if end > start:                       # a shared run: emit it once, recurse past it
        segment = emit(active, start, end, parent)
        yield from build_segments(active, start=end, parent=segment)
        return
    for _, branch in groupby(sorted(active, key=lambda s: s[start]),
                              key=lambda s: s[start]):
        yield from build_segments(list(branch), start, parent)   # split by next token

That's the shape of it, simplified from ART's actual walk in prefix_tree_packing.py. Two refinements matter in practice.
First, a configurable minimum shared-segment length (64 tokens by default) keeps the tree from paying attention-kernel and bookkeeping overhead to share a handful of tokens.
Second, sharing currently excludes trainable tokens for simplicity of loss computation. Trainable tokens likely have different advantages and the advantage tensor is the same length as the token ids tensor (matching to their respective tokens), so you can't overlap trainable tokens without changing how this is handled. I have an idea for generalizing the losses/algorithms in ART and how to support prefix tree packing on that which will replace this and probably allow sharing trainable tokens, which I'll get to in the next month or so.
Finally, an off-by-one note, each branch keeps one duplicated, non-trainable context token right at its join point, so it still gets its own next-token query position when the model is asked to predict the first token that's actually unique to the branch, since it will have a unique loss.

One tree, not one per group

A simple boundary to draw is one tree per RL group — that's where shared prefixes are supposed to live. ART draws no such boundary. Every tokenized completion queued for a training step, regardless of which group or task it came from, walks into one tree together. A system prompt repeated across ten unrelated tasks becomes one shared root the same way a GRPO group's prompt does; the walk doesn't know or care that they're “different groups” — it only knows token sequences. The same goes for a handful of SFT completions distilled from one source, or a batch of eval rollouts replaying the same tool schema: none of it needs a group in the RL sense to benefit from the tree.
You can also just fill in the bins as you go, checking the size of the tree at each step, starting a new one when you can't fit the next trajectory. But it's a little more fun and there's a little more potential gain if you think about and solve it more generally.

What comes with that generality is that deciding which leaves land in which row becomes bin packing: partition a set of items with individual costs into the fewest fixed-capacity bins. Drawing an arbitrary tree-per-group boundary would have sidestepped that problem entirely, at the price of every shared prefix that happens to fall on the wrong side of the boundary. Alternatively, in-order is just a simple bin-packing heuristic. ART takes the trade the other way: pay for a real (NP-hard) bin-packing pass, get back every sharing opportunity actually present in the batch.

That trade is measurable. On a synthetic batch of 48 RL groups spread across three task families — math, tool-use, code review — all sharing one 350-token system prompt and packed into 4096-token rows, building the tree independently per group and only then bin-packing needs 66 rows; pooling everything into one global tree first needs 61 — about eight percent fewer rows purely from where the sharing boundary was drawn, with the bin-packing algorithm itself held fixed. The full historical comparison, including what ART's packing looked like before any of this existed, is at the end.

The same global-tree-then-bin-pack computation gets reused for planning, too. ART's pipeline autotuner estimates how many packed rows a candidate set of groups would need by running this exact tree-and-bin-pack pass over sampled subsets of past data, before ever committing to a training step's batch composition — the same machinery that packs a step also gets asked “what if” questions about how to build the next one.

Bin packing, with a twist

Bin packing — fixed-size items, fixed-capacity bins, minimize bins used — is one of the oldest NP-hard problems around, so which heuristic to reach for is a real decision, not an afterthought (Claude's words, honestly probably not that important to most inputs, but fun to think about and nice to choose something pretty general). First-fit and best-fit decreasing are the standard practical answers: sort items largest-first, then drop each one into whichever open bin leaves the least leftover space (opening a new bin only if nothing fits). ART uses a best-fit-decreasing variant.

But the tree changes what “item size” even means. A leaf's total token count is fixed, but its marginal cost of joining a particular bin is not: any segment that bin already contains — because a sibling landed there first — is free. Classical bin packing has no notion of one item making another cheaper. Here it's the whole point. 

class _PrefixTreeBin:
    def __init__(self):
        self.leaves = []
        self.occupied_segments = set()
        self.token_count = 0

    def insertion_delta(self, leaf):
        return sum(
            length for segment_id, length in leaf.segment_path
            if segment_id not in self.occupied_segments
        )

    def add(self, leaf):
        self.token_count += self.insertion_delta(leaf)
        self.occupied_segments.update(sid for sid, _ in leaf.segment_path)
        self.leaves.append(leaf)


def _place_prefix_tree_leaves(groups, *, seq_len):
    # empty_bin_cost is just the full, unshared length
    ordered = sorted(groups, key=lambda g: max(leaf.empty_bin_cost for leaf in g),
                      reverse=True)
    bins = []
    for leaf in (leaf for group in ordered for leaf in group):
        best_bin, best_remaining = None, seq_len + 1
        for candidate in bins:
            count = candidate.token_count + candidate.insertion_delta(leaf)
            # this fill most heuristic (inherited from best-fit-decreasing) is a little odd, say you have two equally full bins, it
            # will pick the one that shares fewer tokens. But, practically I could not
            # show one generally performed better on semi-realistic workloads than the other, so we stick with this
            if count <= seq_len and seq_len - count < best_remaining:
                best_bin, best_remaining = candidate, seq_len - count
        if best_bin is None:
            best_bin = _PrefixTreeBin()
            bins.append(best_bin)
        best_bin.add(leaf)
    return bins

Trimmed directly from ART's preprocessing/pack.py — a leaf's segment_path is the list of (segment_id, length) pairs on its root-to-leaf path in the global tree, and empty_bin_cost is its full, unshared length. Everything else is ordinary best-fit-decreasing; insertion_delta is the only place the tree shows up at all.

Worth being honest about: once item cost depends on what's already in the bin, this isn't bin packing in the strict textbook sense any more — the classical proofs behind first-fit and best-fit decreasing assume fixed item sizes. It's still NP-hard, and best-fit-decreasing over the real marginal cost is a principled thing to do, but it doesn't inherit the same tight approximation guarantee as its fixed-size ancestor. If you want the precise framing (and where a more principled algorithm might come from), see the appendix.

Token-mixing layers

Packing is useful if token mixing layers are causal, i.e. a token may attend only to its own ancestor chain, never a sibling branch or an unrelated tree packed into the same row. This is prefix caching and radix attention in vLLM and SGLang respectively, just for training.

The pattern that holds for every layer below except GDN: the attention kernel itself never changes, only the input we build for it does. For ordinary masked attention, flex/flash kernels already accept an arbitrary mask specification — a token's tree-correct visible set just decomposes into one fully-visible block per ancestor segment plus a causal triangle over its own segment, exactly the two primitive shapes those kernels already special-case. Building that mask correctly is the whole job; most blocks in a packed row end up empty and get skipped entirely, and the kernel is none the wiser.

Same pattern, different input shape. ART's sparse top-k indexer attention variants (GLM-5.2- and DeepSeek-V4-style) don't take a mask — their attention kernels (sparse_mla, sparse_attn_tilelang) already just gather and attend over whatever key/value indices they're handed, because that's what top-k sparse attention over long context looks like whether or not anything is packed. So the kernel doesn't change here either. All the tree-awareness lives one level up, in the indexer: it only ever scores or constructs candidates from a query's actual ancestor chain, using the same pre-order/exit-order interval check as the mask above, so a sibling branch's keys are never even proposed, let alone selected.

GDN (Gated DeltaNet) is the layer that actually needs new work. It's recurrent — there's no mask to compute, only a running state that has to be threaded token by token, forked once per branch point, and reset at every tree root. ART's GDN planner walks the tree depth by depth; at each depth, every segment across every tree in the packed batch — regardless of which row or group it came from — gets coalesced into exactly two kernel calls: one varlen causal-conv call and one varlen delta-rule call, using the same flash-style cu_seqlens layout an unpacked batch would use. 

# the shape of it: one pass per tree depth, two kernel calls per pass
state_cache = {}
for depth, bucket in enumerate(tree_segment_buckets_by_depth):
    init_conv, init_state = fork_parent_states(bucket, state_cache)   # zero-copy expand
    conv_out = causal_conv1d_varlen(bucket.qkv, init_conv, cu_seqlens=bucket.cu_seqlens)
    rec_out  = chunk_gated_delta_rule(conv_out, init_state, cu_seqlens=bucket.cu_seqlens)
    state_cache[bucket.family_indices] = (conv_out.final_state, rec_out.final_state)
    scatter(rec_out, rows=bucket.row_indices, positions=bucket.position_indices)

A child's initial state is a zero-copy broadcast view of its parent's final state — a plain .expand(), so autograd sums gradients from multiple children back into it for free; root segments start from a zeroed state. One wrinkle: the delta-rule kernel can only fork state cleanly at a fixed chunk boundary (64 tokens), so a branch point whose length isn't a multiple of 64 gets its ragged tail replayed once per child — cheap, at most 63 extra tokens per child. (This gets substantially hairier once context parallelism is involved — cross-rank state exchange, chunk-boundary alignment across ranks — but that's its own post.)

Metadata space first

None of the planning above touches a real tensor. Segment boundaries, group and parent ids, bin assignments — the entire packing plan is computed over plain integers: sequence indices and lengths. Only once a bin's final leaf set is fixed does ART do a single materialization pass that slices real token ids, logprobs, advantages, and (when present) MoE routing-replay data into the packed tensors.

Large per-token payloads, like MoE routing-replay bundles, are kept as lazy segment lists until that pass and sliced exactly once each: 

def iter_slices(self, start, end):
    slices, offset = [], 0
    for segment in self.segments:
        segment_end = offset + segment.shape[0]
        overlap_start, overlap_end = max(start, offset), min(end, segment_end)
        if overlap_start < overlap_end:
            slices.append((overlap_start, segment[overlap_start - offset : overlap_end - offset]))
        offset = segment_end
        if offset >= end:
            break
    return tuple(slices)

And the plan is checked, not just hoped: after placement, ART rebuilds each row's tree locally and asserts it matches the token count computed during global bin-packing before ever writing a tensor — a global-occupancy plan and a bin-local rebuild have to agree, or packing raises rather than silently drifting.

Does it actually help?

Numbers below are from running ART's real packing code (_place_prefix_tree_leaves, prefix_tree_pack_segments) against a synthetic-but-realistic batch: 48 RL groups spread across three task families — math, tool-use, code review — all sharing one 350-token system prompt, packed into 4096-token rows. Same batch as the scope comparison above.

Worth knowing what came before, too. The original version (we called it “shared prefix,” not “prefix tree,” since sharing was exactly one level deep and scoped to a single RL group) deduplicated one whole group prompt at a time under simple in-order row filling. The version that replaced it kept that same in-order, one-row-at-a-time filling, but rebuilt a real multi-segment tree fresh for whatever already happened to be in the current row — a real, shipped design, measured below as “restart-per-row.”

This covers everything above single-node execution. Making the same tree survive being sliced across GPUs under context parallelism — where a branch's tokens might not even live on the same rank as its parent — is a large enough problem for its own post.

Appendix: this isn't quite bin packing

Classical bin packing — fixed-size items, fixed-capacity bins, minimize bins used — assumes an item's cost doesn't depend on what else shares its bin. ART's version doesn't have that property: a leaf's marginal cost of joining a bin is insertion_delta, which depends on which segments that bin already contains. That changes what “item size” means, so it's worth being precise about what's preserved and what isn't.

Still NP-hard

Any classical bin-packing instance embeds trivially: give every item its own private segment, shared with nothing. insertion_delta then reduces to plain fixed item size, and tree-packing specializes exactly to ordinary bin packing. The reduction is immediate; the decision problem stays NP-complete.

What the cost structure actually is

A bin's occupied-token count is the size of the union of every segment referenced by its assigned leaves. Union-size is a monotone submodular (coverage) function of the assigned set: it never decreases as leaves are added, and the marginal gain of adding one more leaf — exactly insertion_delta — can only shrink as more leaves that already cover its segments get added first. So the precise statement of the problem is bin packing where each bin's load is a monotone submodular function of its assigned set, not an additive sum of fixed sizes.

Why the classical guarantee doesn't transfer

The worst-case bounds for first-fit and best-fit decreasing (∼11/9·OPT + O(1)) are proved with arguments that lean on additivity — pairing up under-full bins, volume-counting against total item size. Those proofs don't carry over to a submodular load function. Submodularity does give subadditivity (f(S∪T) ≤ f(S) + f(T)), enough to recover some constant-factor bound via a similar volume argument, but a looser one than the tight classical result. Best-fit-decreasing over true marginal cost is a principled generalization of the standard heuristic, not one with a matching proof of near-optimality.

Where the heuristic leaves value on the table

Sorting leaves by empty_bin_cost — standalone, worst-case size — is the natural analogue of “decreasing,” but it's blind to shareability. Two leaves can have identical standalone cost while one shares heavily with whatever's already placed and the other shares nothing; cost-sorting alone can't tell them apart, only the online best-fit search discovers the difference after the fact. Keeping sibling leaves adjacent in the placement order (grouping by originating tree-family, ordering families by their most expensive member) is a partial mitigation, not a fix for the ordering problem itself.

More principled directions (untested)

No proven superior ratio for this exact problem shape is being claimed here — these are just plausible next places to look: a placement score that weighs segment overlap alongside remaining capacity, not best-fit alone; walking the tree in a locality-preserving order (e.g. depth-first) so segment reuse is discovered by construction instead of by luck of the best-fit search; or borrowing from the submodular-cover literature (Wolsey's greedy submodular-cover result gives a 1 + ln(max cost)-type guarantee for a related, though not identical, covering formulation). For a cost structure this non-standard, the credible way to know whether any of these actually beats what's here is the same way the numbers earlier in this post were produced — measured on real or realistic batches, not reasoned out from bin-packing theory alone.
